## 第 0 期 — 可玩的单人局（MVP）· 已完成

微信小游戏里能走通一局。

- 首页：开始游戏、游戏说明
- 对局：2×2 固定格子；点牌 → 运算符 → 点牌合并。合成牌占后点的格子，并默认选中
- 操作：重开本局、下一局（无撤销）
- 结果：成功 / 失败；结算弹窗不挡住点击
- 3 组写死的有解测试牌，组间循环（第 0 期对局用这三组；第 1 期起对局读全量题库）
- 数字方块，不画扑克；能整除显示整数，否则分数不约分

对局不做：难度入口、提示、统计、音效、扑克图、广告、登录、云。求解器与全量题库在第 1 期离线生成。

## 第 1 期 — 完整数据 · 已完成

- 离线生成全部有解四元组（点数、难度、逐步解法）· 题库已生成（`js/game/puzzles.json`）
- 对局抽题，跳过 `unsolvable` · 已接入
- 已玩 id 存本地，与题库文件分离；抽题优先未玩 · 已接入
- 提示：对局左下角「查看答案」，显示该题 `expression` · 已接入
- 难度：右下角筛选简单 / 中等 / 困难 / 全部，默认简单 · 已接入

## 第 2 期 — 完善细节和美化 · 已完成

- 设置页：总数（发牌计 1 局；重开不加）、成功 / 失败以本局最后一次结算为准、连胜
- 音效开关、音乐开关（默认开；音源已接，见 [audio.md](audio.md)）
- 基础牌面动画（已接入，见 [animation.md](animation.md)）
- 「数字或扑克」已改列入后续，不在本期做

## 第 2.1 期 — 上线 · 进行中

不是第 3 期。目标是把当前可玩版本完成微信小游戏上线（类目、资质、备案、提审、发布）。过程中修小问题、做体验优化。

- 上线当前版本：对局、题库、设置统计、音效 / 音乐、基础牌面动画
- 小修复与优化先记 [test.md](test.md)，讨论后再改代码
- 不接广告、不接支付、不用云
- 难度菜单可打开「含无解题」：默认关，打开后每次发牌有 25% 的机会是无解题，对局可判断「本题无解」
- 数字 / 扑克、两台手机云对战仍在后续计划。同一设备双人对战改为第 2.2 期

交接见 [phase-2.1-handoff.md](phase-2.1-handoff.md)。

## 第 2.2 期 — 同机双人对战 · 已完成

同一台设备上两个人对战。本地完成，沿用现有题库和合牌。先抢答再限时合牌，第一位失败后换对方，先到 5 分获胜。双人题库、难度、统计与单人分开。答题时长默认 20 秒，设置页每次 ±5，夹在 10～60。

定稿见 [phase-2.2-duel.md](phase-2.2-duel.md)。交接见 [phase-2.2-handoff.md](phase-2.2-handoff.md)。两台手机云对战仍留在后续计划。

## 第 2.3 期 — 响应式布局 · 已完成

首页、单人和双人按屏幕尺寸排开，避免矮屏重叠。设置页不改。844×390 这种极矮横屏不纳入本期。

方案见 [ux/issue-49-responsive-layout.md](ux/issue-49-responsive-layout.md)。交接见 [phase-2.3-handoff.md](phase-2.3-handoff.md)。

- 双人竖屏用居中单列，内容宽不超过 430
- 横屏先试三栏，排不开就退回居中单列，不恢复 748–927 的旧双栏
- 单人牌桌按剩余高度缩小；首页「来挑战一下」到「单人游戏」至少留 40px
- 难度菜单用带描边的卡片托住选项；单人仍在按钮上方，双人三栏从按钮右侧展开

## 第 2.4 期 — 体验收口 · 进行中

第 2.3 期之后的小修复，并上线当前版本。先做已经有结论的条目，不改玩法。优先领先皇冠、小房子避开前置摄像头。游戏说明和设置在放不下时可以滚动，「返回」留在屏内，按下时与首页大按钮一样轻微缩放。运算符可点区域按和第二行牌的间距向上、向下各扩一半。上线步骤与第 2.1 期相同：类目、资质、备案、提审、发布；不接广告、不接支付、不用云。切后台暂停倒计时和「下一局」确认已 `won't fix`。

交接见 [phase-2.4-handoff.md](phase-2.4-handoff.md)。

## 第 3 期 — 广告和收入

开工前：企业主体、流量主。客户端已定为小游戏。

- 每 20 局广告一次
- 简单免费；中等 / 困难对免费用户一次激励视频
- 0.99 一天免广告；9.90 终身免广告
- 不做自定义金额打赏
